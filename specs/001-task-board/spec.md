# Спецификация: Коллаборативная доска задач (Trello-like)

- Статус: accepted
- Версия: 1.0
- Дата: 2026-11-12

## 1. Обзор

Веб-приложение для совместной работы с задачами в формате канбан-досок:
колонки, карточки, перетаскивание (drag-n-drop), обновления в реальном времени
для всех участников доски. Бэкенд использует WebSocket (Socket.IO), предусмотрен
механизм шаринга досок через invite-ссылки.

## 2. Глоссарий

| Термин | Значение |
|---|---|
| Доска (Board) | Набор колонок и карточек, принадлежит пользователю |
| Колонка (Column) | Список карточек на доске, упорядоченный |
| Карточка (Card) | Задача: заголовок, описание, позиция в колонке |
| Участник (Member) | Пользователь, имеющий доступ к чужой доске |
| Invite-ссылка | Ссылка с токеном для вступления в доску |
| Комната | WS-группа Socket.IO `board:<id>`, события рассылаются в её пределах |

## 3. Пользовательские истории

### Аккаунты
- **US-1.** Как посетитель, я могу зарегистрироваться (email + пароль), чтобы получить аккаунт.
- **US-2.** Как зарегистрированный пользователь, я могу войти и выйти, чтобы защищать свой аккаунт.
- **US-3.** Как пользователь, я вижу список «Мои доски» (созданные мной + доски, куда меня пригласили) и могу создать новую доску.

### Доска
- **US-4.** Как владелец/участник доски, я вижу колонки и карточки доски, чтобы работать с задачами.
- **US-5.** Как участник, я могу создавать, переименовывать и удалять колонки.
- **US-6.** Как участник, я могу создавать карточки с заголовком, редактировать заголовок/описание и удалять их.
- **US-7.** Как участник, я могу перетаскивать карточки внутри колонки и между колонками (drag-n-drop), а также менять порядок колонок; на сенсорном устройстве могу перенести карточку в другую колонку, выбрав колонку в открытой карточке (без перетаскивания).
- **US-8.** Как участник, я вижу изменения других участников мгновенно (≤ 1 с после действия): новые/изменённые/удалённые/перемещённые карточки и колонки, изменения появляются без перезагрузки страницы.
- **US-9.** Как участник, я вижу список подключённых сейчас к доске (presence) и индикатор «кто редактирует эту карточку».

### Шаринг
- **US-10.** Как владелец доски, я могу сгенерировать invite-ссылку с токеном и сроком действия.
- **US-11.** Как неавторизованный/чужой пользователь, перешедший по invite-ссылке, я могу присоединиться к доске (при необходимости — после регистрации/входа).
- **US-12.** Как владелец, я могу отозвать invite-ссылку (после отзыва вход по ней невозможен) и видеть список участников доски.

## 4. Функциональные требования

### 4.1 Аккаунты
- FR-1. Регистрация: email (уникальный, валидируется форматом) + пароль (мин. 8 символов), форма требует **повторного ввода пароля** и отклоняет несовпадение; пароль хранится в виде bcrypt-хеша (cost ≥ 10).
- FR-2. Сессия: JWT в httpOnly-cookie (SameSite=Lax, срок 7 дней). Выход удаляет cookie.
- FR-3. Дубликат email при регистрации и неверные креды при входе возвращают понятную ошибку формы.

### 4.2 Доски и контент
- FR-4. Новая доска создаётся с колонками по умолчанию: `To Do`, `In Progress`, `Done`.
- FR-5. Карточка имеет: заголовок (1–200 симв.), опциональное описание (≤ 5000), позицию, колонку, автора, метки времени.
- FR-6. Порядок карточек/колонок — дробная позиция (float/numeric), соседние элементы при вставке дают среднее позиций; при нехватке точности позиции колонки перенормировываются.
- FR-7. Drag-n-drop охватывает: карточка → другая позиция той же колонки, карточка → другая колонка, порядок колонок. Во время перетаскивания видна заглушка-«тень» на **будущем месте**, и сохранённая позиция обязана совпадать с ней (WYSIWYG); отпускание вне колонок отменяет перенос. На сенсорных устройствах доступен альтернативный способ: открыть карточку и выбрать целевую колонку в поле «Колонка».
- FR-8. Все мутации контента (создание/изменение/удаление/перемещение) доступны **только через WS-события** — HTTP REST используется для auth, списка досок, CRUD досок и шаринга.
- FR-9. Подключение к доске: клиент по WS отправляет `board:join`; сервер проверяет доступ и добавляет сокет в комнату `board:<id>` и отправляет полный снапшот доски.
- FR-10. Каждая мутация от клиента валидируется (zod) и по правам; только владелец может удалять доску и управлять шарингом.

### 4.3 Реал-тайм
- FR-11. Сервер авторитетен: он применяет мутацию, пишет в БД и рассылает событие всем сокетам в комнате (включая автора — клиент сверяет optimistic-состояние с ответом).
- FR-12. События содержат минимальные delta (id + изменённые поля + позиция), а не весь снапшот.
- FR-13. Присоединившийся к середине участник получает актуальный снапшот (никаких ручных sync-очередей).
- FR-14. Presence: сервер рассылает `presence:update` (список пользователей в комнате) при входе/выходе/disconnect; редактируемая карточка помечается userId в `card:editing-start/stop`.

### 4.4 Шаринг
- FR-15. Invite-ссылка: `GET /join/:token` — если токен валиден (не истёк, не отозван) и пользователь авторизован, он становится участником и попадает на доску; иначе — редирект на логин с сохранением целевой ссылки.
- FR-16. Токен — случайная строка (≥ 32 симв.), хранится в БД с полями `boardId, expiresAt, revokedAt, createdBy`.
- FR-17. Список участников доски виден всем участникам; удаление участников из версии 1 не входит.

## 5. Нефункциональные требования

- NFR-1. **Стек:** TypeScript (strict) на клиенте и сервере; React + Vite; Node.js ≥ 20 + Express + Socket.IO; PostgreSQL; ORM — Drizzle (drizzle-kit); валидация — zod в пакете `shared`.
- NFR-2. **Структура:** pnpm workspaces monorepo — пакеты `client`, `server`, `shared`.
- NFR-3. Задержка отображения чужого изменения ≤ 1 с в нормальных условиях (время рассылки события).
- NFR-4. Точность позиций: не менее 1000 вставок подряд в середину колонки без сбоя порядка.
- NFR-5. Безопасность: пароли — bcrypt; JWT — httpOnly cookie; проверка прав на каждую мутацию; инъекции исключены ORM-параметризацией.
- NFR-6. **Деплой:** Docker Compose на арендованном VPS — `app` (сборка client+server) + `postgres` + обратный прокси Caddy с автоматическим TLS; БД — PostgreSQL в Compose (том для данных).
- NFR-7. Конфигурация через env-переменные (`.env`, `.env.example` в репозитории); секреты в репозиторий не попадают.
- NFR-8. Ошибки WS/HTTP — единый формат `{ error: { code, message } }`.
- NFR-9. **CI/CD из GitHub (GitHub Actions):** CI — на каждый push и PR выполняются install/typecheck/lint/build; CD — при пуше в `main` автоматический деплой на VPS по SSH (rsync исходников → `docker compose build && up -d`). Доступ runner'а к серверу — по выделенному SSH-ключу из секретов Actions; секреты в репозитории не хранятся.
- NFR-10. **Автономный локальный запуск:** на машине без сети, Docker и PostgreSQL проект полностью работает (`pnpm install && pnpm dev`): при отсутствии `DATABASE_URL` сервер сам поднимает встроенный PostgreSQL (embedded-бинарники, данные локально); локальная БД не синхронизируется с продовой.

## 7. Критерии приёмки (сводно)

| # | Критерий | Проверка |
|---|---|---|
| A1 | Два браузерных профиля: A перетаскивает карточку — у B позиция меняется ≤ 1 с, без F5 | Ручное демо |
| A2 | Присоединение третьего участника «в середине» показывает актуальное состояние | Ручное демо |
| A3 | Invite-ссылка из инкогнито-окна ведёт к регистрации → доске; повторный вход — сразу к доске | Ручное демо |
| A4 | Отозванная ссылка не пускает нового пользователя | Ручное демо |
| A5 | Обновление страницы не теряет данные (перезагрузка = снапшот из БД) | Ручное демо |
| A6 | `pnpm dev` поднимает всё локально; `docker compose up` — на VPS с HTTPS | Проверка команд |
| A7 | Невалидные WS-сообщения отклоняются с ошибкой, состояние не портится | Ручной тест |
