# Спецификация v2: доска задач как продукт (дизайн, доступы, аккаунты, доски)

- Статус: draft (на утверждение)
- Версия: 2.0-draft
- Дата: 2026-11-16
- Основание: продолжение `specs/001-task-board/spec.md` (v1, тег `v1.0`).
  Все требования v1 сохраняются, кроме явно изменённых или отменённых здесь.

## 1. Обзор

v1 — рабочее ядро (аккаунты, доски, drag-n-drop, real-time, шаринг), но по уровню
продукта это техно-демо. v2 доводит приложение до состояния, которым можно
пользоваться: современный интерфейс с тёмной темой, полноценное управление
доступами, аккаунт с контактами и подтверждением почты, управление досками
(архив, избранное, поиск, шаблоны колонок), автотесты и стабильный API-контракт,
на который сможет опереться будущий десктоп-клиент.

## 2. Глоссарий (дополнения к v1)

| Термин | Значение |
|---|---|
| Роль | Права участника на конкретной доске: OWNER, ADMIN, EDITOR, VIEWER |
| Подтверждённый email | Адрес, владелец которого перешёл по ссылке из письма |
| Архив | Скрытая из основного списка доска с возможностью восстановления |
| Шаблон колонки | Сохранённый набор «название + карточки» для быстрой вставки |
| Контакты | Описание, телефон, мессенджеры в профиле (все поля опциональны) |
| e2e-тест | Автотест Playwright, проходящий реальные сценарии в браузере |

## 3. Пользовательские истории

### Интерфейс
- **US-13.** Как пользователь, я хочу современный аккуратный интерфейс с тёмной темой, чтобы работать без усталости глаз и не стесняться показывать продукт.
- **US-14.** Как пользователь телефона, я хочу удобно работать с доской пальцем, чтобы не испытывать трудностей с мелкими элементами.

### Доступы
- **US-15.** Как владелец доски, я хочу назначать администраторов, чтобы делегировать управление участниками.
- **US-16.** Как владелец/админ, я хочу приглашать людей по email и видеть, кто уже в доске, чтобы управлять составом.
- **US-17.** Как владелец, я хочу удалять участника из доски, чтобы ограничить доступ.
- **US-18.** Как участник с ролью «просмотр», я не должен иметь возможности случайно изменить чужую работу.

### Аккаунт
- **US-19.** Как пользователь, я хочу заполнить профиль (имя, описание, телефон, мессенджеры), чтобы коллеги знали, как со мной связаться.
- **US-20.** Как пользователь, я хочу сменить пароль, чтобы обезопасить аккаунт.
- **US-21.** Как пользователь, я хочу подтвердить email, чтобы получить полный доступ (создание досок, редактирование).
- **US-22.** Как пользователь, я хочу видеть контакты участников общей доски, чтобы связаться с ними.

### Доски
- **US-23.** Как пользователь, я хочу убирать ненужные доски в архив и восстанавливать их, чтобы не терять данные.
- **US-24.** Как пользователь, я хочу отмечать доски избранными и искать по названию, чтобы быстрее находить нужное.
- **US-25.** Как пользователь, я хочу сохранять колонку как шаблон и вставлять шаблон в доску, чтобы не создавать одно и то же вручную.

## 4. Функциональные требования

### 4.1 Интерфейс и дизайн

- FR-19. UI строится на **shadcn/ui + Tailwind CSS**: дизайн-токены (цвет, типографика, отступы, радиусы) в CSS-переменных; компоненты — из shadcn/ui. Текущий самописный CSS заменяется постепенно, без «большого взрыва».
- FR-20. **Тёмная тема**: переключатель «системная / светлая / тёмная», выбор сохраняется; по умолчанию — системная. Все экраны и состояния читаемы в обеих темах (контраст не ниже WCAG AA для текста).
- FR-21. Адаптивность: телефон (от 360 px), планшет, десктоп. Тап-цели ≥ 44×44 px, горизонтальный скролл колонок на телефоне, доступные модалки на маленьком экране.
- FR-22. Единые состояния экранов: загрузка (скелетоны), пусто (подсказка действия), ошибка (сообщение + повтор), отсутствие прав (объяснение, а не пустой экран).

### 4.2 Доступы и роли

- FR-23. Роли на уровне доски: **OWNER → ADMIN → EDITOR → VIEWER**.

  | Действие | OWNER | ADMIN | EDITOR | VIEWER |
  |---|---|---|---|---|
  | Просмотр доски | ✅ | ✅ | ✅ | ✅ |
  | Изменение контента (колонки, карточки, перемещения) | ✅ | ✅ | ✅ | ❌ |
  | Приглашение участников и управление ими | ✅ | ✅ | ❌ | ❌ |
  | Переименование доски | ✅ | ✅ | ❌ | ❌ |
  | Назначение/снятие ADMIN | ✅ | ❌ | ❌ | ❌ |
  | Удаление и архивирование доски | ✅ | ❌ | ❌ | ❌ |

- FR-24. Владелец видит список участников с ролями, может менять роль (EDITOR ↔ VIEWER), назначать и снимать ADMIN, удалять участника (кроме владельца). При удалении участника **отзывается ссылка, по которой он вступил** — повторно войти по ней нельзя.
- FR-25. Приглашения: ссылка с токеном (как в v1) создаётся владельцем/админом; при вступлении участник получает роль **EDITOR** по умолчанию (роль можно указать при создании приглашения).
- FR-26. Приглашение **по email**: владелец/админ указывает адрес и роль → уходит письмо со ссылкой, привязанной к этому адресу. Вступление возможно только с этим адресом; для незарегистрированного — регистрация с возвратом на доску.
- FR-27. Каждая мутация проверяется на сервере по роли (WS и REST); UI лишь скрывает недоступные действия. Попытка запрещённого действия возвращает `ws:error` с понятным кодом (`FORBIDDEN`) и не меняет данные.

### 4.3 Аккаунт

- FR-28. Профиль: имя (обязательно), описание (≤ 500 символов), телефон, мессенджеры (список «тип + значение»: Telegram, WhatsApp, другое) — **все, кроме имени, опциональны**.
- FR-29. Контакты видны другим аутентифицированным пользователям, состоящим с владельцем профиля в общей доске (через карточку участника в шапке доски).
- FR-30. Смена пароля: требуется текущий пароль, новый — минимум 8 символов; после смены все прочие сессии инвалидируются.
- FR-31. Подтверждение email: при регистрации отправляется письмо со ссылкой (токен одноразовый, срок 24 ч). Статус отображается в профиле, есть повторная отправка (не чаще 1 раза в минуту).
- FR-32. Пользователь с **неподтверждённым** email: может просматривать доски, в которых состоит; **не может создавать доски**, приглашать участников и редактировать содержимое досок, где не является владельцем. В собственных досках права сохраняются.
- FR-33. «Выйти на всех устройствах»: инвалидация всех сессий пользователя, кроме текущей.

### 4.4 Почта

- FR-34. Отправка писем через абстракцию `Mailer` с режимами: `console` (письмо в лог/файл — режим по умолчанию для локальной разработки и офлайн-запуска), `smtp` (прод).
- FR-35. Прод-провайдер — **Яндекс SMTP** (`smtp.yandex.ru`, 465/SSL или 587/STARTTLS, пароль приложения из env). Адрес отправителя настраивается переменной; при отправке с адреса на домене `bibza.ru` потребуется делегирование домена в Яндекс (вне объёма v2, см. §6).
- FR-36. Письма v2: подтверждение email, приглашение на доску. Шаблоны текста — на русском, с явной ссылкой и сроком действия; plain-text + HTML.
- FR-37. Ошибки отправки не ломают основной сценарий: письмо ставится в очередь с 2–3 повторами, пользователь видит «не удалось отправить, повторите позже»; факт и ошибка логируются.
- FR-38. Ограничение частоты: повторная отправка подтверждения — не чаще 1/мин; приглашений на доску — не более 20/час на пользователя.

### 4.5 Доски

- FR-39. **Архив**: владелец может архивировать доску; архивные доски скрыты из основного списка, доступны вкладкой «Архив» и **открываются только для просмотра** до восстановления. Данные не удаляются.
- FR-40. **Избранное**: отметка «в избранном», закреплённый блок в начале списка; состояние хранится на сервере (видно с любого устройства).
- FR-41. **Поиск** по названию доски в списке (регистронезависимый, без задержек на клиенте).
- FR-42. Сортировка списка: по дате изменения (по умолчанию), по названию, избранные — всегда сверху.
- FR-43. **Шаблоны колонок**: системные (набор из 2–3 готовых, например «Разработка», «Учёба») и пользовательские — «сохранить колонку как шаблон» (название + карточки, без исполнителей и ролей). Вставка шаблона при создании колонки. Пользовательские шаблоны видны только автору.
- FR-44. Шаблоны и архивирование не меняют существующие карточки и позиции; вставка шаблона создаёт новые сущности в одной транзакции.
- FR-51. **Шаблоны досок**: системные наборы (готовые колонки и карточки) и пользовательские — «сохранить доску как шаблон». Создание доски из шаблона копирует структуру одной транзакцией, не меняя доску-образец. Пользовательские шаблоны видны только автору.

### 4.6 UX-полировка

- FR-45. Клавиатурные сценарии на доске: переход между колонками/карточками, открытие карточки (Enter), закрытие (Esc), создание карточки/колонки.
- FR-46. Обратная связь: тосты для успешных и неуспешных действий, подтверждение необратимых операций (удаление, архивирование), сохранение позиции скролла при обновлениях.
- FR-47. Доступность: фокус-стили, подписи у иконок (`aria-label`), работа модалок с клавиатуры, отсутствие «ловушек» фокуса.

### 4.7 API для будущего десктоп-клиента

- FR-48. Единый документ контракта `docs/api-contract.md`: REST-эндпоинты, WS-события, формат ошибок, требования к авторизации. Документ — источник истины для десктоп-проекта.
- FR-49. Стабильность контракта: изменения WS/REST в v2 не ломают существующие события и поля (только аддитивно). Версия API доступна в `GET /api/health` (поле `apiVersion`).
- FR-50. Способы авторизации не-браузерных клиентов: основной — та же cookie-сессия (клиент хранит cookie); при необходимости по итогам spike — аддитивный `POST /api/auth/token` (Bearer, короткоживущий), не заменяющий cookie-поток для веба.

## 5. Нефункциональные требования

- NFR-11. Стек UI: shadcn/ui + Tailwind CSS; React 19 + Vite сохраняются. Сторонние UI-библиотеки не вводятся без пересмотра спецификации.
- NFR-12. Существующие требования v1 сохраняются: server-authoritative, единый zod-контракт в `shared`, real-time ≤ 1 с, офлайн-запуск `pnpm dev` без БД и сети.
- NFR-13. Офлайн-режим разработки: без настроенного `Mailer` письма пишутся в лог/файл; `pnpm dev` работает без интернета.
- NFR-14. e2e-тесты Playwright запускаются **по требованию** (локально, на чекпоинтах фаз и перед релизом), а не на каждый push; при падении сохраняются скриншоты и трейсы.
- NFR-15. Миграции БД — только аддитивные и обратимые по смыслу: существующие доски/участники/карточки не теряются; роли существующих участников заполняются значениями по умолчанию.
- NFR-16. Безопасность не ослабевает: проверка прав на каждую мутацию, bcrypt, httpOnly-cookie, лимиты на почту, одноразовые токены подтверждения.

## 6. Вне объёма v2

Дублирование доски; метки, дедлайны, чек-листы и вложения карточек (v3);
системная админ-панель (управление всеми пользователями); удаление аккаунта; смена email
в аккаунте; i18n;
собственный почтовый сервер (Postfix/Dovecot);
десктопный клиент (отдельный проект, отдельная спецификация).

## 7. Критерии приёмки

| # | Критерий | Проверка |
|---|---|---|
| V1 | VIEWER не может изменить контент (UI скрывает, сервер отклоняет) | e2e + ручная |
| V2 | ADMIN управляет участниками, но не удаляет доску; OWNER назначает админов | e2e |
| V3 | Приглашение по email: письмо приходит, ссылка работает только для этого адреса | e2e + ручная (Яндекс SMTP) |
| V4 | Подтверждение email: письмо, переход по ссылке, статус в профиле; ограничения FR-32 работают | e2e |
| V5 | Профиль и контакты сохраняются и видны участникам общей доски | ручная |
| V6 | Смена пароля инвалидирует прочие сессии; «выйти везде» работает | e2e |
| V7 | Архив: скрытие/восстановление; избранное; поиск; сортировка | e2e |
| V8 | Шаблоны колонок и досок: сохранение и вставка создают корректные колонки и карточки | e2e |
| V9 | Тёмная тема и адаптив: все экраны читаемы, телефон 360 px без горизонтального скролла страницы | ручная + скриншоты |
| V10 | Регресс v1: A1–A8 проходят; десктоп-контракт (`docs/api-contract.md`) актуален | e2e + ревью |

## 8. Совместимость и миграции

- `board_members.role`: существующие владельцы → OWNER, остальные участники → EDITOR.
- `users`: добавляются `emailVerifiedAt`, `description`, `phone`, `messengers` (jsonb), `tokenVersion` (для инвалидации сессий).
- Новые таблицы: `email_verifications` (токен, срок, использован), `column_templates`, `board_templates`.
- `boards`: `archivedAt`; избранное — персонально для участника: `board_members.favorite`.
- Существующие инвайты продолжают работать; поле роли в инвайте — со значением по умолчанию EDITOR.

## 9. Риски

| Риск | Митигация |
|---|---|
| Объём рестайла на shadcn/ui затянется | этап A идёт первым; миграция покомпонентно; Playwright-«дым» до перестройки |
| Яндекс SMTP: ограничения на отправителя (нужен ящик на Яндексе или делегирование домена) | отправитель = адрес аккаунта; делегирование домена — вне v2; в спеке зафиксировано |
| Письма попадают в спам | отправка через Яндекс (репутация), plain-text + HTML, без ссылок-сокращателей |
| Роли ломают существующие WS-сценарии | проверки прав централизуются в одном хелпере, покрываются e2e |
| Десктоп потребует изменений API | контракт фиксируется документом и версией; изменения — только аддитивные |
