# Конституция проекта Task Board

Принципы, которым подчиняется вся разработка. Любое изменение кода не должно им противоречить;
изменить конституцию можно только осознанно, отдельным коммитом с объяснением в PR/коммите.

## 1. Spec-Driven Development
- Сначала документ (`specs/`), потом код. Спека — единственный источник правды.
- Любое изменение требований сначала отражается в `spec.md` / `plan.md`, и только потом в коде.
- Каждая фаза из `tasks.md` заканчивается проверяемым результатом (checkpoint), а не «примерно готово».

## 2. TypeScript везде
- Строгий режим (`strict: true`) во всех пакетах; `any` запрещён, кроме оправданных границ (JSON.parse и т.п.) с комментарием.
- Контракты (типы протокола WS, DTO, схемы валидации) живут в пакете `shared` и импортируются и сервером, и клиентом. Дублирование типов запрещено.

## 3. Сервер — источник истины
- Клиент отправляет **намерения** (intent), сервер валидирует, применяет, сохраняет в БД и рассылает **события** всем в комнате.
- Оптимистичный UI на клиенте разрешён, но обязан сверяться с событием от сервера (reconciliation).
- Клиент никогда не доверяет входным данным: всё, что приходит по WS/HTTP, валидируется (zod) на сервере.

## 4. Один язык на весь стек
- TypeScript, ESM (`"type": "module"`), общие конфиги (tsconfig, eslint, prettier) в корне.
- Именование: camelCase в коде, kebab-case в именах файлов, PascalCase в типах/компонентах.

## 5. Малые проверяемые шаги
- Ветки под задачи: `feat/…`, `fix/…`, `chore/…`; main собирается и запускается всегда.
- Коммиты по Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`, `refactor:`).
- Мёртвого кода и TODO без задачи не оставляем.

## 6. Демо — часть требований
- Проект обязан запускаться локально одной командой (`pnpm dev`) и на VPS через Docker Compose.
- Если шаг «поднять и посмотреть» не описан в README, фаза не считается завершённой.
